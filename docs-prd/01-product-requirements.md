# 01 — Product Requirements (Backend)

## 1. Problem

The Punta web app (`/web`) is a fully clickable product with **no backend**:

- Auth stores a SHA-256 password hash in `localStorage`. The "session" cookie is just the raw user id.
- Products, portfolio, theme and POS register are saved in `localStorage`, keyed by user id.
- Orders, customers, inventory, wallet, expenses, deliveries, campaigns, bookings, packages and POS history are **in-memory seed data** and reset on every reload.
- Analytics and the main dashboard cards are hardcoded numbers.
- The public storefront (`/store/**`) shows **the logged-in user's own data**. There is no way for a real shopper to visit a merchant's store.

`largecom` must become the single source of truth, so the app works across devices, across users, and for real shoppers.

## 2. Users

| User | Where | Needs |
|:--|:--|:--|
| **Merchant (owner)** | `/dashboard/**` | Sign up, set up a store, sell, see money |
| **Staff** (manager / fulfillment) | `/dashboard/**` | Limited access, invited by owner |
| **Shopper / client** | `/store/**` on `slug.punta.shop` | Browse, buy, book, contact |
| **Platform** (us) | Webhooks, jobs | Payments, payouts, domain checks |

## 3. Business modes

The merchant picks one mode in Settings. It changes the sidebar (`web/src/lib/nav.ts`). The backend stores the mode, and every module works regardless of the mode. The mode is a UI concern, not a permission.

| Mode | Core modules |
|:--|:--|
| `ecommerce` | Products, orders, POS, customers, inventory, messaging, analytics, expenses, deliveries, store, wallet |
| `pos` | POS, shift history, products, inventory, customers, expenses, analytics, wallet |
| `portfolio` | Portfolio, bookings, packages, messaging, analytics, store, wallet |

## 4. Functional requirements

Priority: **P0** = needed for launch, **P1** = launch if time allows, **P2** = after launch.

### 4.1 Auth & account — P0
- **FR-A1** Register with `storeName`, `email`, `password`. This creates a user, a tenant (store) with a unique slug derived from the store name, and an owner membership. The user is logged in immediately.
- **FR-A2** Login with email + password. Errors must not reveal whether the email exists (the frontend currently shows "No account found"; change it to one generic message).
- **FR-A3** Logout revokes the refresh token and clears cookies.
- **FR-A4** `GET /me` returns user, active tenant, role, `hasOnboarded`, `businessMode`.
- **FR-A5** Passwords: at least 8 characters (the frontend currently allows 6; update it), hashed with Argon2id.
- **FR-A6** Forgot / reset password by email — P1.

### 4.2 Onboarding & templates — P0
- **FR-O1** `POST /onboarding` with a `templateId` does all of this in **one transaction**:
  - applies the theme template
  - seeds the template's categories, products and portfolio items
  - sets `hasOnboarded=true`
- **FR-O2** Templates live on the backend: `studio-minimal`, `boutique` (default / "Skip"), `bold-market`, `classic-craft`, `photography-portfolio`. Port them from `web/src/lib/theme/templates.ts` and `web/src/lib/products/industry-catalogs.ts` into JSON resource files.
- **FR-O3** Re-applying a template later (`/dashboard/store/theme/templates`) replaces the theme only. It keeps custom pages and does **not** re-seed products.

### 4.3 Store settings — P0
- **FR-S1** One source of truth for store name, tagline, support email and phone, currency (NGN), VAT % (7.5 default), `notifyOnNewOrder`, `autoFulfillDigital`, `businessMode`.
- **FR-S2** Changing the store name also updates `theme.global.storeName`. The frontend currently keeps three copies; the backend owns one.

### 4.4 Theme / storefront builder — P0
- **FR-T1** Store the full theme document in the frontend's own shape: `global`, `header`, `footer`, `about`, `contact`, `shop`, `sections[]`, `pages[]`, `navLinks[]`, `templateId`.
- **FR-T2** The editor's **Save** button sends the whole document (`PUT /theme`). Use optimistic locking (`version`) so two tabs can't silently overwrite each other.
- **FR-T3** Validate section `type` against the 9 known types and custom-page slug uniqueness. Store the settings themselves as JSON.
- **FR-T4** Do not store editor UI state (`selectedSectionId`, `activePageId`, `selectedIs*`).
- **FR-T5** Draft vs published theme — P1. In v1, a save is live immediately.

### 4.5 Catalog — P0
- **FR-C1** Categories: list, create (idempotent by slug, as `addCategory` behaves today), rename, delete (P1).
- **FR-C2** Products: create, update, delete (soft), toggle active, toggle featured, list with search (name / SKU / tag) and status filter.
  - The slug is generated by the server and is unique per tenant. It is regenerated when the name changes.
- **FR-C3** Product fields exactly as `web/src/lib/products/types.ts`: `priceKobo`, `compareAtKobo`, `costKobo`, `sku`, `barcode`, `tags[]`, `emoji`, `swatch`, `imageUrl`, `isActive`, `isFeatured`.
- **FR-C4** Variants: add, update, remove. `priceKobo = null` means "use the product price". Attributes are a free key/value map.
- **FR-C5** Image upload. Dev: store on local disk. Prod: S3/R2 presigned upload. Return a URL; never store data URLs.

### 4.6 Inventory — P0
- **FR-I1** **One stock system.** Stock is tracked per location in `inventory_levels`. A product's `stock` in API responses is the sum across locations. Every tenant gets a default location ("Main Store") at registration.
- **FR-I2** Adjust stock (+/−, with a reason), and record every change as an `inventory_movement`.
- **FR-I3** Status is computed: `out_of_stock` when stock is 0, `low_stock` when stock ≤ `reorderPoint`, `in_stock` otherwise.
- **FR-I4** Orders and POS decrement stock **atomically**, with no oversell. Fail with `409 INSUFFICIENT_STOCK`.
- **FR-I5** Multiple locations and transfers — P1.

### 4.7 Customers — P0
- **FR-CU1** CRUD; search by name, email or phone; filter by group (`VIP | Returning | New | Wholesale`).
- **FR-CU2** `totalOrders`, `totalSpentKobo` and `lastOrderDate` are **derived from orders**, not typed in.
- **FR-CU3** Orders link to `customerId`. A manual or POS order with a new phone or email can create the customer automatically.

### 4.8 Orders — P0
- **FR-OR1** Manual order (`/dashboard/orders/new`): customer, items, shipping address, payment status.
  - The server prices the items from the catalog. Never trust client prices, except for an explicit manual override (P1).
- **FR-OR2** Per-tenant order number `ORD-1001`, `ORD-1002`, … used by **all** channels, including POS.
- **FR-OR3** Update fulfillment status (`pending → processing → shipped → delivered`, or `cancelled`). Cancelling restocks the items.
- **FR-OR4** List with search (order number, name, email) and status filter; KPIs (paid revenue, pending + processing, shipped, delivered).
- **FR-OR5** Order fields: `channel` (`web|whatsapp|instagram|manual|pos`), `paymentStatus` (`paid|unpaid|refunded`), `paymentMethod` (`cash|card|transfer|null`).
- **FR-OR6** Invoice PDF — P2.

### 4.9 POS — P0
- **FR-P1** Open a register with an opening float; only one open register per user (multi-register is P1 via `enableMultiRegister`).
- **FR-P2** `POST /pos/checkout` in **one transaction**:
  - creates the order (`channel=pos`, `paid`, `delivered`)
  - decrements stock
  - adds to the session's per-method totals
  - requires an `Idempotency-Key` header, so a double-tap never double-charges
- **FR-P3** Close the register with the counted cash; the server computes expected cash and over/short.
- **FR-P4** Shift history and sales history come from **real sessions and orders**, with filters for today / 7d / 30d. `POSDailySummary` is computed, not stored.
- **FR-P5** Receipt settings (`showStoreName`, `showStorePhone`, `footerMessage`, `autoPrint`, `defaultPaymentMethod`, `enableVat`, `vatPercent`, `enableMultiRegister`). VAT is applied at checkout when enabled.
- **FR-P6** Record the cashier (the logged-in user) on each session and sale.
- **FR-P7** CSV export of sales — P1.

### 4.10 Portfolio mode — P0
- **FR-PF1** Portfolio items: CRUD and toggle featured. The slug comes from the title.
- **FR-PF2** Service packages: CRUD, toggle active or popular, `sortOrder`, reorder (P1).
- **FR-PF3** Booking inquiries:
  - **public** create from `/store/book`
  - dashboard create
  - status change (`new → contacted → confirmed | declined`)
  - KPIs: pending count, confirmed count, pipeline value (sum of package prices for confirmed inquiries), response rate
- **FR-PF4** Email the merchant on a new inquiry, and email the client a confirmation — P1.

### 4.11 Public storefront — P0
- **FR-SF1** Resolve the tenant from the `Host` header (`acme.punta.shop`, or a verified custom domain) or from the `X-Store-Slug` header (dev and preview).
- **FR-SF2** Read-only public endpoints:
  - store and theme
  - active products (with category filter and `sort=newest`)
  - product by slug, with active variants
  - featured products
  - portfolio items, and a portfolio item by slug
  - active packages
  - custom page by slug
- **FR-SF3** Public writes:
  - booking inquiry
  - contact message (when `contact.showForm` is on)
  - newsletter signup
  - All three are rate-limited and have a honeypot field.
- **FR-SF4** Never return inactive products, cost price, inventory internals, or customer data.

### 4.12 Cart, checkout & payments — P1 (launch target)
- **FR-PAY1** Cart kept server-side, keyed by an anonymous cart token cookie.
- **FR-PAY2** Checkout creates an order (`channel=web`, `unpaid`), **reserves** stock, and initializes a Paystack transaction. Returns `paymentUrl`.
- **FR-PAY3** Paystack webhook: verify the `x-paystack-signature` HMAC-SHA512, then process idempotently. On success the order is marked `paid` and a wallet settlement entry is recorded. On failure or expiry the reservation is released.

### 4.13 Wallet — P1
- **FR-W1** The wallet is an append-only **ledger**. The balance is derived from the entries, never stored as a mutable number.
- **FR-W2** Shows available balance, pending balance (T+1 settlements), lifetime payouts, and transactions (`payout | order_settlement | addon_fee | topup`, signed amounts, status).
- **FR-W3** Payout request: a saved settlement bank account, amount ≤ available balance. v1 creates a `pending` payout that is processed manually; automating it with Paystack Transfers is P2.

### 4.14 Expenses — P0
- **FR-E1** CRUD; categories `Inventory | Marketing | Logistics | Utilities | Staff`; search; category filter.
- **FR-E2** Summary: total for the period, top category with its %, and net margin (revenue − expenses) / revenue.

### 4.15 Deliveries — P1
- **FR-D1** Book a delivery **for an order** (`orderId`, not a free-text order number): courier, address, ETA, tracking code.
- **FR-D2** Update status: `pending → in_transit → delivered | action_required`.
- **FR-D3** Courier APIs (Shipbubble, GIG) — P2. v1 works with manual entry.

### 4.16 Messaging — P1
- **FR-M1** Campaigns: `name`, `channel` (`whatsapp | sms | email`), audience (customer group or "all"), **`messageBody`** (the frontend currently drops it; store it), status `draft | scheduled | sent`, `scheduledAt`.
- **FR-M2** Sending runs in the background. Email first (Resend or SMTP); SMS and WhatsApp sit behind the same interface and come in P2.
- **FR-M3** Stats (`sentCount`, open and click rates) come from real delivery events, never faked.

### 4.17 Team — P1
- **FR-TM1** Invite by email with a role (`Manager | Fulfillment Staff`). The invite is `Pending` until accepted through an emailed link.
- **FR-TM2** Roles map to permissions (see [03](./03-backend-architecture.md#authorization)).

### 4.18 Domains — P1
- **FR-DM1** Every tenant has `slug.punta.shop`.
- **FR-DM2** Custom domain flow: the merchant enters a domain, and the server returns the DNS records (`CNAME www → cname.punta.shop`, plus a TXT verification token). A "Verify" action performs a real DNS lookup. The domain becomes active only after verification succeeds.

### 4.19 Analytics & dashboard — P0 (basic) / P1 (full)
- **FR-AN1** Dashboard cards for each mode, computed from real data:
  - ecommerce: 30-day revenue with % change, orders, new customers, live products
  - POS: today's sales, 30-day revenue, average ticket, open registers
  - portfolio: item count, pending inquiries, confirmed bookings, active packages
- **FR-AN2** Analytics page, with range `7d | 30d | 90d | 1y`:
  - revenue time series
  - AOV
  - repeat-customer rate
  - top products
  - channel breakdown
  - storefront conversion (needs page-view events, P1)

## 5. Non-functional requirements

| Area | Requirement |
|:--|:--|
| **Data safety** | See [07](./07-database-safety.md). No path in code, config or tests can drop the DB. |
| **Isolation** | No API can return another tenant's row. Proven by a cross-tenant integration test per module. |
| **Money** | Integer kobo (`long` / `BIGINT`) everywhere. No `double`, no `BigDecimal` in the API. |
| **Consistency** | Order + stock + register (+ wallet) updates are single DB transactions. |
| **Idempotency** | POS checkout, payment webhooks and payout requests are safe to retry. |
| **Performance** | p95 < 200 ms for dashboard reads at 10k products / 100k orders per tenant. |
| **Security** | Argon2id, httpOnly cookies, CSRF-safe, rate-limited auth and public endpoints, secrets only in env vars. |
| **Observability** | Structured JSON logs with `requestId` and `tenantId`; `/actuator/health`; error rates. |
| **Compliance** | NDPR: marketing consent flag on customers; customer data export and delete (P1). |

## 6. Out of scope (v1)

- Native mobile app and offline POS
- Paystack Transfers automation (payouts are processed manually in v1)
- WhatsApp Commerce (catalog sync, bot), which is Phase 2 in `docs/PUNTA/roadmap/week-13.md`
- Multi-currency
- Add-on billing and subscription tiers (keep the `addon_fee` transaction type, no purchase flow yet)
- KYC (BVN/NIN): required before automated payouts, so P2

## 7. Success criteria for v1

1. Two merchants register on different machines. Each sees only their own data.
2. A merchant onboards with a template, edits the theme, adds products, and the store is visible at `acme.localhost:3000` (dev) or `acme.punta.shop` (prod) to a logged-out visitor.
3. POS: open register → 3 sales → close register. Stock, orders, shift history and dashboard all agree.
4. A shopper books a package on `/store/book`, and it appears in `/dashboard/bookings` on another device.
5. A full restart of backend + DB loses nothing. Re-running the app never changes the schema.
